How this app works

A chapter-by-chapter walkthrough of the codebase — what it is, how a request flows through it, and where every important thing lives. Written to be read top to bottom, framed against the MERN stack you already know.

Chapter 1 — What is this app?

This is “vysi”, a mobile-first Progressive Web App for the town of Valenza, Italy. It’s a single codebase that hosts three small products (“modules”) behind one login:

ModuleWhat the user doesRoute
AdventurePlays a GPS-based narrative game — walk to real locations, unlock story, make choices./adventure
CommunityReports neighborhood problems (litter, broken benches…) by dropping a photo pin on a map; volunteers mark them fixed./community
AssociationsBrowses a directory of local volunteer associations on a map + list, and contacts them./associations

Everything else — login, registration, Google sign-in, profiles, an admin panel, internationalisation (English / Italian / Spanish), dark mode — is shared plumbing that all three modules sit on top of.

Mental model Think of it as one Express + React app, except Express and React live in the same project and the same files. Next.js is the framework that fuses them: your “Express routes” are files under app/api/**, and your “React app” is files under app/**. There is no separate backend server to start.

The 30-second tour of the repo

app/ → pages (React) AND api routes (backend) — the App Router api/ → backend endpoints (your "Express routes") (auth)/ → login, forgot-password, reset-password pages adventure/, community/, associations/, dashboard/, profile/, admin/ components/ → shared React components (layout chrome lives in layout/) contexts/ → React Context providers (Auth, Locale, Theme, Chrome, Consent) modules/ → the 3 pluggable features (each: manifest + components + lib) lib/ → server-side utilities (auth, prisma, permissions, env, email, storage) config/ → modules.ts (the registry of active modules) locales/ → en.ts / it.ts / es.ts translation dictionaries prisma/ → schema.prisma (the DB model), migrations/, seed.ts __tests__/ → Vitest integration + unit tests
The golden rule for reading this codebase CLAUDE.md at the repo root is the authoritative spec — architecture, conventions, and deployment steps. When code and CLAUDE.md disagree, the doc wins. Read it early.

The biggest surprise In MERN your frontend (port 3000) and backend (port 5000) are separate apps that talk over CORS. Here they’re the same app on one port. A page component and the API it calls are compiled together. No CORS, no separate deploy.

Chapter 3 — A request, end to end

Let’s trace “a logged-in user loads the Community map and reports a problem.” This shows every layer working together.

Browser (PWA) Next.js server Postgres ───────────── ────────────── ──────── 1. GET /community ──────▶ app/community/page.tsx (React page) renders shell + <CommunityMap/> (client component, 'use client') 2. useCommunityNotices() ──▶ GET /api/community/notices ───▶ SELECT open notices (hook, on mount) (public, no token needed) strip user_id, add isOwn ◀────── { data: { notices:[...] } } 3. tap +Report, submit ────▶ POST /api/community/notices/upload-url (needs auth) requireAuth → presigned R2 URL ◀────── { uploadUrl, key } PUT photo ──────────────▶ Cloudflare R2 (object storage) 4. POST /api/community/notices (Authorization: Bearer <accessToken>) requirePermission('community','create') rate-limit check (1/day, 3/week) Zod validate body ───────────▶ INSERT CommunityNotice ◀────── 201 { data: { notice } } 5. hook prepends notice to state → map re-renders with the new pin

The shapes every endpoint uses

This contract is universal in the codebase — learn it once:

// success
{ "data": { ...whatever } }              // HTTP 200 / 201

// error
{ "error": "human message", "code": "MACHINE_CODE" }   // 400/401/403/404/500

A typical route handler reads like this (simplified from a real one):

export async function POST(request: NextRequest) {
  // 1. AUTH: returns a NextResponse (401/403) OR { user }
  const result = await requirePermission(request, 'community', 'create')
  if (isNextResponse(result)) return result

  // 2. PARSE: never trust the body — Zod validates it
  const parsed = createNoticeSchema.safeParse(await request.json())
  if (!parsed.success)
    return NextResponse.json({ error: '...', code: 'VALIDATION_ERROR' }, { status: 400 })

  // 3. DO THE WORK: Prisma writes, filtered by the caller's id
  const notice = await prisma.communityNotice.create({
    data: { userId: result.user.sub, ...parsed.data },
    select: { id: true, /* only the fields the client needs */ },
  })

  // 4. RESPOND in the standard shape
  return NextResponse.json({ data: { notice } }, { status: 201 })
}
Four steps, every time auth → validate → work → respond. Once you’ve read one route you can read them all. Chapter 4 explains step 1; Chapter 5 explains step 3.

Chapter 4 — Auth & permissions

Two questions get answered on every protected request: “who are you?” (authentication) and “are you allowed?” (authorization / RBAC).

Tokens: access vs refresh

TokenLifetimeStored wherePurpose
Access (JWT)15 minReact memory only (never localStorage)Sent as Authorization: Bearer … on API calls.
Refresh (JWT)30 dayshttpOnly cookie; hashed in the DBMints a new access token when the old one expires.

The magic that makes short-lived access tokens invisible to the user lives in contexts/AuthContext.tsx as fetchWithAuth:

fetchWithAuth('/api/...') → send with Bearer accessToken → 401? ──▶ POST /api/auth/refresh (uses the httpOnly cookie) → got new accessToken → retry the original request once → still 401 → user is logged out

Refresh tokens rotate: every call to /api/auth/refresh revokes the old token and issues a new one (see app/api/auth/refresh/route.ts). Password reset and account deletion revoke all refresh tokens, forcing re-login.

Login is “unified”

There is one entry point. POST /api/auth/login checks if the email exists:

  • Exists → verify the password → issue tokens.
  • Doesn’t exist → return { needsRegistration: true }. The frontend then shows step 2 (name + privacy consent) inline, and submits to POST /api/auth/register. No user row is created until consent is given (a GDPR rule).

Google OAuth (app/api/auth/google/*) follows the same idea: new OAuth users land on /complete-profile to accept the privacy terms; returning ones go straight to /dashboard.

RBAC: roles + direct permissions

Permissions are strings shaped resource:action (e.g. adventure:play, community:create, associations:manage). A user can get a permission two ways:

  1. Role-based — the permission is attached to a role, and the user has that role (role_permissions table).
  2. Direct — an admin grants the exact permission to one user (user_permissions table).

The gatekeeper is requirePermission(request, resource, action) in lib/permissions.ts. It:

  • reads the JWT → 401 if missing/invalid;
  • lets master_admin and admin bypass all checks;
  • otherwise loads the user’s merged permission set (cached in-process for 60s) → 403 if the permission isn’t present.

Sibling helpers: requireAuth (just “logged in?”) and requireAdmin (“is an admin?”). New module permissions default to admin-only until you add them to the userAllowlist in prisma/seed.ts.

The security boundary you must never remove Permissions decide which feature you can touch. But every user-facing query is also filtered by userId (from the JWT’s sub). That WHERE userId = me is what stops user A from reading user B’s data. Deleting a permission check is bad; deleting the userId filter is a breach.

Chapter 5 — Data & Prisma

The database is PostgreSQL. The schema is one file: prisma/schema.prisma. From it, Prisma generates a fully-typed client you import as prisma from lib/prisma.ts.

Prisma vs Mongoose Instead of a Mongoose schema per collection, you write one model block per table in schema.prisma. Instead of User.find(), you write prisma.user.findMany() — and TypeScript knows the exact return shape. Relations are real foreign keys, not manual populate().

The main tables

GroupModels
Auth / RBACUser, Role, Permission, UserRole, RolePermission, UserPermission, RefreshToken, PasswordResetToken
AdventureGame, GameLocation, GameSession, SessionParticipant, SessionFlag, LocationVisit
CommunityCommunityNotice (+ CommunityNoticeStatus enum: open / fixed)
AssociationsAssociation

House rules for data access

  • IDs are cuid() strings. Every foreign key has an explicit index.
  • Always use select — return only the columns the client needs, never whole rows. (This is also how sensitive fields like user_id get stripped from public responses.)
  • List endpoints paginate (?page=1&limit=20) and always filter on an indexed column.
  • Never expose userId to clients; compute a boolean like isOwn instead (see the Community list route).

Migrations & seeding

Changing the schema is a two-step ritual:

# 1. edit prisma/schema.prisma, then:
npx prisma migrate dev --name add_something   # creates + applies a migration, regenerates the client

# 2. seed reference data (idempotent — safe to re-run):
npx prisma db seed

prisma/seed.ts creates the roles, the permissions (read from the active modules!), the master admin, demo bot users, and the 37 Valenza associations. It’s written with upsert so running it twice never duplicates.

Prod migrations differ On the server you run npx prisma migrate deploy (applies pending migrations, no shadow database), not migrate dev. See Ch. 8.

Chapter 6 — The module system

The three products are pluggable. Each lives under modules/<name>/ and declares itself with a manifest:

// modules/associations/manifest.ts
const associationsManifest: ModuleManifest = {
  id: 'associations',
  name: 'Associations',
  isActive: true,
  navItem: { label: 'Associations', href: '/associations', icon: 'HeartHandshake' },
  permissions: ['associations:manage'],   // seeded automatically
  apiPrefix: '/api/associations',
  testEndpoint: '/api/associations/manage', // used by the RBAC test sweep
}

The registry config/modules.ts imports every manifest and exports activeModules = [...].filter(m => m.isActive). That single array drives a lot:

  • the nav (Sidebar + BottomNav map over it to render links);
  • the seeded permissions (seed.ts reads activeModules[].permissions);
  • the RBAC test (rbac.test.ts hits each testEndpoint).

To disable a module you flip isActive:false — its nav link disappears and its permissions stop being seeded (so RBAC blocks its routes). To add one you create a manifest, add Prisma models, register it, and add pages + API routes. (That’s exactly how the Associations module was built.)

How each module is laid out

modules/<name>/ manifest.ts → the declaration above components/ → module-only React components (sheets, maps…) lib/ → module logic: schemas.ts (Zod), hooks, helpers app/<name>/page.tsx → the page the user sees app/api/<name>/... → the module's backend endpoints

What’s interesting inside each

  • Adventure — a little flag-based state machine. Visiting a location checks a visibleWhen condition, verifies your GPS is within radiusM metres (haversine.ts), then grants/revokes flags that unlock later locations. Choices and password-locked spots use a “callback flag” trick. There’s even read-only spectator multiplayer via a 6-char join code.
  • Community — photo pins with a rate limit (1/day, 3/week per user), a public map anyone can read, and a “mark fixed” flow with before/after photos. Photos go to Cloudflare R2 via presigned URLs.
  • Associations — a public read directory (map + searchable list); only admins can add/edit/delete. Picks one “preferred” contact per entry (website → Facebook → Instagram → email).

Chapter 7 — The frontend

Server components vs client components

This is the concept that trips up every MERN dev. In a CRA/Vite SPA, all your React runs in the browser. In Next.js App Router, components render on the server by default, and only become interactive in the browser if the file starts with 'use client'.

Server component (default)Client component ('use client')
RunsOn the server, at request timeServer (SSR) then hydrates in the browser
Can useasync/await, DB, secretshooks (useState, useEffect), events, browser APIs
Exampleapp/page.tsx (landing)app/community/page.tsx (interactive map)
Why the landing page is split app/page.tsx is a tiny server component that renders components/LandingPageClient.tsx. This exists for SEO: an earlier all-client version showed Googlebot only a loading spinner. The rule now: any public/indexable page must render its content without a “if (loading) return <spinner>” gate.

State that’s shared everywhere: Contexts

ContextGives you
AuthContextuser, login/logout/register, and fetchWithAuth (the auto-refreshing fetch).
LocaleContextt('some.key') translation function + locale + setLocale (en/it/es).
ThemeContextlight / dark / system, persisted to localStorage.
ChromeContexthideChrome — full-screen pages (the map screens) hide the header/nav.
ConsentContextcookie/analytics consent state.

The app “chrome” & route protection

  • components/layout/Sidebar.tsx (desktop), BottomNav.tsx (mobile), Header.tsx (mobile top bar) — all read activeModules for their links and hideChrome to disappear on full-screen pages.
  • components/layout/ProtectedRoute.tsx wraps private pages: it waits for auth to load, redirects to /login if you’re not signed in, and to /complete-profile if you haven’t accepted the privacy terms.

Internationalisation

No i18n library — just locales/en.ts, it.ts, es.ts. en.ts exports the authoritative Translations type, so if you add a key to English and forget the other two, TypeScript won’t compile. You call const { t } = useLocale() then t('associations.title').

iOS Safari + Leaflet gotcha On the map pages, overlays use position: absolute inside a relative parent — never position: fixed or React portals (Leaflet clips them on iOS). And never add a Leaflet Tooltip to markers — it breaks taps on iOS.

Chapter 8 — Run, test & deploy

Running locally

npm run dev      # dev server on http://localhost:3000 (hot reload)
npm run build    # production build
npm run lint     # ESLint
npx prisma studio  # visual DB browser

Testing

Tests live in __tests__/ and run with Vitest. Most are integration tests: they hit a running server and a real test DB (TEST_DATABASE_URL). A few (the adventure engine) are pure unit tests.

# IMPORTANT: bypass Nginx's rate limiter or you'll get 503s
NEXT_PUBLIC_APP_URL=http://localhost:3000 npm test

Helpers in __tests__/helpers.ts (registerAndLogin, authHeaders, uniqueEmail) make writing a test three lines long. The rbac.test.ts sweep automatically covers every module’s testEndpoint for the 401/200 boundary.

Deploying (VPS + PM2 + Nginx)

There is no deploy script — you run these in order on the server:

npm install                                # only if deps changed (NEVER npm ci — SIGBUS on low-RAM VPS)
npx prisma migrate deploy                  # only if schema changed
pm2 stop all                               # MUST stop before building
npm run build
pm2 reload ecosystem.config.js --update-env
pm2 save
Deploy pitfalls to remember
  • Stop PM2 before building — a running app reading a half-written .next/ crashes.
  • Stale chunks — after a deploy, hard-refresh (Ctrl+Shift+R). An open PWA keeps running old JS until fully reloaded.
  • Cookies use sameSite:'lax', not strict — otherwise Google OAuth’s redirect breaks the login.

ecosystem.config.js runs two things: the Next.js app in 2-worker cluster mode, and a digest-new-users cron that emails a daily signup summary at 16:00 UTC. nginx.conf is the reverse proxy and rate-limiter in front of it.
